# producthub 部署与发布(Railway)

> 目标:**上线的代码与开发代码隔离**,**更新方式确定**,且**更新不影响线上数据**。
> 思路:Git 分支隔离(开发在 `dev`,线上分支 `main`)+ 版本标签;schema 一律走 Alembic 迁移,
> 启动时自动 `upgrade head`(追加式);数据住在 Railway Postgres + uploads 卷里,发布只换代码不碰数据。

## 运行形态

- 开发(本机):后端 `uvicorn app.main:app --reload` + 前端 Vite dev(5173 代理到 8000),库 `producthub`。
- 线上(Railway):仓库根 `Dockerfile` 由 Railway 云端构建;**一个 web 服务**同时托管 API(/api)、
  图片(/uploads)与前端页面(SPA 兜底);数据库用 **Railway Postgres 插件**;上传文件在
  **volume**,挂到 `/app/uploads`。

```
浏览器 → Railway web 服务(uvicorn: /api 路由 → /uploads 静态 → 前端 dist 兜底)
          ├─ 启动时先 alembic upgrade head(空库首建 / 旧库增量)
          └─ 数据:Postgres(插件)+ /app/uploads(volume),重建不丢
```

## 代码隔离与版本

| 分支 | 用途 |
| --- | --- |
| `main` | **线上分支**。Railway 监听它,推送到 `main` 即自动上线;只接受 dev 合并而来的、已测版本 |
| `dev` | 日常开发分支。所有未完成/半成品都在这,永远不会自动上线 |

- 发布点打标签 `vX.Y.Z`(标记版本,方便回溯与对代码)。
- 首次基线:`v0.1.0` = 当前五张表结构 + 部署文件。

## 首次上线(Railway,从零)

前置:已安装并登录 GitHub、Railway。

1. 建 GitHub 私有仓库并推送本仓库:
   ```bash
   gh repo create producthub --private --source=. --remote=origin --push   # 或网页建仓后手动推
   ```
2. Railway 新建项目:
   - **New Project → Deploy from GitHub repo** → 选 `producthub` → Service 指向 `main`。
   - Railway 识别根目录 `Dockerfile` 云端构建;每次 push `main` 自动触发部署。
3. 数据库:
   - **New → Database → PostgreSQL** 创建插件,并把它 **Link/附到** web 服务;
     Railway 自动注入 `DATABASE_URL`(应用已兼容无驱动后缀的 URL,见 `app/db.py`)。
   - 首次部署时入口会自动 `alembic upgrade head`,在空库上建出全部表。
4. 上传文件持久化(重要):
   - 给 web 服务 **New → Volume**,Mount Path 填 **`/app/uploads`**(对应 `UPLOAD_DIR` 默认值),
     与 web 服务同 Region。不挂卷的话,每次部署的新容器里 `uploads/` 是空的,图片会"消失"。
5. (建议)Settings → Health Check Path 填 `/api/health`;`PORT` 由 Railway 注入,无需手填。
6. Variables 里配齐下面的环境变量(表见后一节),至少 `APP_BASE_URL`(指向本服务的 `*.up.railway.app`
   https 域名)与 `ADMIN_EMAIL` / `ADMIN_PASSWORD`(首启引导建第一个管理员)、`SMTP_*`(发邀请/重置邮件)。

部署后访问 Railway 分配的 `*.up.railway.app`:页面、接口、图片全部同源。第一次打开应跳到登录页,
用启动时自动创建的管理员账号登录;建完用户账号后可移除 `ADMIN_EMAIL/ADMIN_PASSWORD`。

## 环境变量(Railway Variables)

| 变量 | 必填 | 说明 |
| --- | --- | --- |
| `DATABASE_URL` | 是 | Postgres 连接串(Railway Postgres 插件会自动注入);容器入口先 `alembic upgrade head` 再起服务 |
| `APP_BASE_URL` | 线上必填 | 应用对外地址,如 `https://xxx.up.railway.app`。**决定两件事**:① 邀请/重置邮件里链接的前缀;② cookie 是否带 `Secure`(仅 https 站点才带,本地 http 才能正常登录)。不填时默认 `http://localhost:5173`,线上邀请链接会指错 |
| `SMTP_HOST` + `SMTP_FROM` | 用 SMTP 时必填 | 走 stdlib smtplib 发信;**若走下方 `RESEND_API_KEY`,这两个可省(只留 `SMTP_FROM`)** |
| `RESEND_API_KEY` | 用 Resend 时填 | 填了就走 **Resend HTTP API**(`https://api.resend.com/emails`,443),后端不再碰 SMTP 端口。**Railway/部分云平台封 SMTP 出站(smtp 连接 timed out、Resend 后台查不到记录)时,用它根治**,只需 `RESEND_API_KEY` + `SMTP_FROM` 即可;值就是那把 `re_…` API key(与 `SMTP_PASSWORD` 同一把) |
| `SMTP_PORT` | 否 | 默认 `587`(STARTTLS)。**若平台封 587 出站(如部分云环境连 smtp 超时),改 `465`** = SMTPS 隐式 TLS,后端自动走 `SMTP_SSL`;仍不通则切 `RESEND_API_KEY` 走 HTTP(443) |
| `SMTP_STARTTLS` | 否 | 仅 `587` 等普通端口生效,默认开;自建/内网 SMTP 需明文时设 `"0"`(`465` 不需要它) |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | 多数服务需要 | SMTP 登录账号与授权码(发件服务常见;QQ 邮箱用授权码,Resend/Mailgun 用 API key 当密码) |
| `SMTP_FROM_NAME` | 否 | 发件显示名,默认 `producthub` |
| `ADMIN_EMAIL` + `ADMIN_PASSWORD` | 首次启动 | 仅当**库里一个账号都没有**时生效:启动自动创建第一个管理员(幂等)。**建议只在首启时配置,管理员建好用户账号后即可从 Railway 移除这两个变量** |
| `ADMIN_NAME` | 否 | 首个管理员的显示名,默认「管理员」 |
| `DEEPSEEK_API_KEY` | 用 AI 时必填 | **AI 助手的唯一必填项**。不填 = 「AI 未配置」的状态(**不是报错**):界面显示「未配置」,提问接口 503,站内其它功能完全不受影响。余额从这里扣 |
| `AI_MODEL` | 否 | 默认 `deepseek-flash`。**模型名绝不硬编码** —— DeepSeek 已经改过一轮命名,`deepseek-v4-flash` 现在是退役别名。可选 `deepseek-v4-pro`(更强更贵) |
| `AI_BASE_URL` | 否 | 默认 `https://api.deepseek.com`。只有走自建代理 / 官方换域名才需要改 |
| `AI_WALL_CLOCK_BUDGET` | 否 | 一次提问的**总时间预算**(秒,默认 `120`),到点就把已经拿到的部分交出去、标上「不完整」。**这个值是真 key 实测后定的**(一次往返 1.8–2.7 秒),调小是安全的,代价只是长回答可能被截。⚠️ **第七版起它止不住花钱**:到点我们只是不再接收后续事件,内核那一轮仍在跑(SDK 没有取消接口)。v6 能当场关掉上游连接,v7 只能少花「后续轮次」的钱 —— 见 `ai_harness.run_question` |
| `AI_REASONING_EFFORT` | 否 | 思考档位:**`off` / `low` / `high` / `max`**,不给**效果就是 `high`** —— 但机制值得说清:不给 = 这个字段**根本不发**,由服务端决定;官方文档(2026-09 核实)写的是「思考模式默认开,默认 effort 就是 `high`」,所以落回 `high`。**不是 dsh 挑的 `high`**,dsh 那侧省略就只是省略。要省钱 / 提速设 `low`(官方还接受 `medium` / `xhigh`,但内部都映射成 `high`,写了等于没写)。⚠️ 第七版起它是**实例级**配置(建 agent 时定,不是每次请求给),改了要等池子里的旧实例退场 —— 已经进了缓存键,所以**下一次提问**就生效 |
| `DSH_PROFILE` | 否 | dsh 的 profile 名,默认 `sdk-minimal`。**改它等于换一套工具和插件** —— 那个 profile 里我们才关掉了持久化 shell(`persistent-bash` / `persistent-pwsh`)和会上传会话日志的 `session-log-deepseek`。换 profile 前先看 `ai_harness` 模块头的安全说明 |
| `AI_DSH_HOME` | 否 | dsh 的工作目录,默认项目根 `.dsh/`。**必须可写**;镜像里固定为 `/app/.dsh`(见 Dockerfile)。里面是会话 JSONL 和按提问者生成的 patch,**不要挂卷**:历史由 Postgres 重放,那里面存的是我们刻意放弃的东西 |
| `AI_DSH_WORKSPACE` | 否 | 给 dsh 的 cwd,默认 `<dsh_home>/workspace`,**是个空目录**。模型没有文件类工具,所以它碰不到;存在的意义只是满足运行时的 cwd 要求。⚠️ **不要指向仓库根** —— 万一将来误开了某个文件工具,爆炸半径会从「一个空目录」变成「整个仓库」 |
| `AI_HARNESS_IDLE_TTL` | 否 | 一个 dsh 实例空闲多少秒后回收,默认 `600`。实例 = 1 个 node 进程 + 1 个工具子进程,所以这个值决定「闲置用户占着多少内存」。**真机实测(2026-09-17,macOS arm64):一个实例 233MB RSS**(node 运行时 ~160 + 工具子进程 ~72),**一个提问者一个实例** —— 所以 3 个人同时在线 ≈ 700MB,再往上加是线性的。这是这一版真正的容量上限(不是 CPU):**先把 Railway 服务的内存上限对一遍**,不够就调小这个 TTL |
| `AI_HARNESS_START_TIMEOUT` | 否 | 起一个实例的等待上限(秒,默认 `30`)。真机实测 0.5–0.6 秒,慢过这个值说明环境有问题 |

> 小贴士:登录验证走「邮箱 → 邀请链接设密 / 重置临时密码」闭环,没配 SMTP 就只能登录到 bootstrap
> 出的管理员,建不了用户账号。本地先把 `.env` 配好(模板见 `.env.example`)再联调最省事。

> **AI 的限额不在环境变量里** —— 每日提问数 / 单次 token 上限 / 月度预算由**管理员在界面上设**
> (头像菜单 →「AI 设置」)。管理员不是部署者,让人去改 Railway 变量再等重启等于这个旋钮不存在。
> **额度是钱**:月度预算留空 = 不限,上线前想清楚要不要给个保守值。
>
> ⚠️ **上线后必须手工确认一件事:SSE 真的在流**(答案逐字出现,不是等完才一次性出来)。
> 本地测不到 Railway 边缘代理的缓冲行为。若被缓冲,退路是切回非流式 —— 服务端刻意把
> 「生成」(`ai_agent.stream_answer`)与「传输」(路由里的 SSE 包装)分开了,只动路由那一层。

> ⚠️ **AI 这一版假定 uvicorn 是单进程。** 入口是 `uvicorn app.main:app`,**没有 `--workers`**。
> 实例池、每个实例的锁、空闲 TTL 全在**进程内存**里。所以:
> `--workers 2` 或再开一个副本 → 每个提问者被起**两份**实例(内存直接翻倍),
> 而且「同一个人的两次提问串行」这条保证会失效(两个进程各有一把锁)。
> 要横向扩之前先改这里,别只改 worker 数。

## 日常发布/更新流程

```bash
# 1. 在 dev 上开发、本地验证(测试 / 迁移 / pnpm build)
git checkout dev
... 改代码,提交 ...

# 2. 合并到 main,Railway 自动上线
git checkout main
git merge dev            # 建议 --no-ff,保留发布记录
# (可选)git tag vX.Y.Z && git push origin vX.Y.Z
git push origin main     # → Railway 检测到推送,重建容器
```

上线那一刻容器入口自动做:

1. `alembic upgrade head` —— 把新增的迁移跑一遍(**追加式**,只加表/列,不改不删,不动已有数据);
2. 再启动 uvicorn。

**数据安全保证**:

- 数据分两处且都不随"代码更新"变化:记录在 **Postgres**(Railway 托管、跨部署持久),
  图片文件在 **volume**(挂 `/app/uploads`,跨部署持久)。
- schema 变更**只允许**新增 Alembic 迁移,禁止 `create_all` / 手工 `drop` 上线库。
- 迁移前向追加:新版本上线只在旧 schema 上做增量,老数据行原样保留。
- 备份:上线前可选 `pg_dump` 出一份;或直接在 Railway 面板给 Postgres 开每日备份。
- 回滚:在 Railway 该服务的 **Deployments** 历史里,对上一个成功的 Deploy 点 **Redeploy** 即可
  (数据不动;若回滚到旧代码而库已到更新的 head,旧代码也能读(迁移只加不删),不会启动失败)。

## 日常改表(Schema 变更)流程

模型改了(`app/models.py`)之后,在 dev 上生成并提交迁移:

```bash
cd <项目根目录>
python -m alembic revision --autogenerate -m "加个字段"   # 连的是 .env 里的开发库
# 打开 migrations/versions/ 里新生成的脚本,人工核对后再提交(autogenerate 需人工复查)
python -m alembic upgrade head                            # 本地开发库同步
```

要点:

- `migrations/env.py` 的连接串与表元数据都取自应用代码(`app.db` / `app.models`),
  不用改 `alembic.ini`。
- 测试库 `producthub_test` 仍按 `Base.metadata` 现建现删,不进 Alembic 链。
- 提交的迁移会随下次发布在线上自动执行;**永远只追加新迁移,不回改已发布的迁移文件**。
- 想让某台已建好表的库只打标记不重跑:`python -m alembic stamp head`。

## 自托管(可选)

同一份 `Dockerfile` 也能在任意有 Docker 的机器/平台自托管:

```bash
docker build -t producthub .
docker run -p 8000:8000 \
  -e DATABASE_URL=postgresql://user:pass@host:5432/producthub \
  -v producthub_uploads:/app/uploads \
  producthub
```

需要自备 Postgres(首次会在空库上自动建表)。
